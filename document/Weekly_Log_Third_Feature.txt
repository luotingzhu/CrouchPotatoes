3.1 管道结构 / Pipeline shape
--------------------------------------------------------------------------------
  Airflow/手动触发
  Airflow or manual trigger
        │
        ▼
  run_source(source_id)
        │
        ├─ 1) 读取 data_sources，判断 source_type
        │    Load data_sources and branch on source_type
        │      api     → _fetch_api()      调用内置演示接口
        │      crawler → _crawl()          抓取真实站点并解析文章
        │
        ├─ 2) 归一化：标题 / 正文 / URL / publish_time / module_id / 标签
        │    Normalise: title, body, URL, publish_time, module_id, tags
        │
        └─ 3) 投递到 Broker（MVP 为进程内队列，接口与 Kafka 对齐）
              Publish to the broker (in-process queue in the MVP, with a
              Kafka-compatible boundary)

  consume_loop() 常驻消费者 / resident consumer
        │
        ├─ 4) 计算 content_hash = sha256(title + content)
        │    Compute content_hash = sha256(title + content)
        │
        ├─ 5) 去重：按 (source_id, content_hash) 查询，命中则跳过并广播事件
        │    Dedup by (source_id, content_hash); skip and emit an event on hit
        │
        ├─ 6) 写入 raw_data（按月分区），先提交事务
        │    Insert into raw_data (monthly partitions) and commit first
        │
        └─ 7) 事务提交后再向量化并写 embeddings
              Vectorise and write embeddings only after the commit

3.2 为什么先提交再向量化 / Why commit before embedding
--------------------------------------------------------------------------------
  向量化要调用外部 Embedding 服务，耗时且可能失败。
  Embedding calls an external service: slow and fallible.
  如果把它放在数据库事务里，一次网络抖动就会让整批入库回滚。
  Holding the transaction open across that call means one network hiccup
  rolls back the whole batch.
  因此事务边界只覆盖「原始数据落库」，向量化作为后续步骤，失败可重试。
  So the transaction covers only the raw-data write; embedding is a follow-up
  step that can be retried independently.

3.3 去重策略 / Deduplication
--------------------------------------------------------------------------------
  - 分区表无法建全局唯一约束（唯一约束必须包含分区键），
    因此去重放在应用层：先查后插。
    A partitioned table cannot carry a global unique constraint (the key must
    include the partition key), so dedup lives in the application layer:
    check first, then insert.
  - (source_id, content_hash) 上建复合 B-Tree 索引，判重查询走索引。
    A composite B-Tree index on (source_id, content_hash) keeps the lookup
    indexed.
  - 命中重复时不报错、不回滚，只跳过并广播「重复数据已跳过」事件。
    A duplicate is not an error and does not roll back: it is skipped and
    announced as an event.

3.4 每日快照机制 / Daily snapshot mechanism
--------------------------------------------------------------------------------
  问题：演示源内容固定，重复抓取会被去重跳过，导致某模块长期没有新数据。
  Problem: demo content is static, so repeated fetches dedupe away and a
           module can go days without new rows.
  做法：演示源返回的内容末尾追加当日日期标记
        （数据快照日期：YYYY-MM-DD）。
  Approach: each demo item carries today's date marker, so the content hash
            changes once per day.
  结果：每天第一次抓取会真正插入新行；同一天内重复抓取仍然去重。
  Result: the first fetch each day inserts new rows; repeats the same day
          still dedupe.

5.3 三条链路闭环 / Three closed loops
--------------------------------------------------------------------------------
  抓取闭环 / Ingestion loop
    抓取 → 归一化 → Broker → 去重 → raw_data → embeddings
    Fetch → normalise → broker → dedup → raw_data → embeddings
  报告闭环 / Report loop
    订阅模块 → 取数 → LLM 三段合成 → reports / report_sections /
    report_sources → 段落向量化
    Subscribed modules → select rows → three LLM sections → three tables →
    section embeddings
  对话闭环 / Chat loop
    提问 → Redis 缓存 → 向量检索 → LLM 带引用作答 → 三处回写
    Question → Redis cache → vector search → cited answer → write back

  三条链路共用同一批 raw_data 与同一个 embeddings 表，因此不是三个独立演示。
  All three share the same raw_data and the same embeddings table, so they are
  not three separate demos.

六、技术决策与理由 / 6. Decisions and Rationale
================================================================================

  1. 抓取与入库解耦（Broker 在中间）
     Fetch and persist are decoupled by a broker
     理由：抓取慢且易失败，入库需要稳定；解耦后可削峰、可重放。
     Why: fetching is slow and fragile while persistence must be reliable;
          decoupling allows buffering and replay.

  2. 事件总线放在进程内，而不是引入 Kafka 做演示
     The event bus stays in-process instead of standing up Kafka for a demo
     理由：演示只需要「可观察」，不需要跨进程持久化；接口边界保留，
           后续替换不影响业务代码。
     Why: the demo needs observability, not cross-process durability; the
          boundary is kept so it can be swapped later without touching
          business logic.

  3. 状态接口每次实时查询，不做缓存
     The status endpoint queries live every time, no caching
     理由：这个页面的价值就是「所见即真实」，缓存会让它退化成另一个假数据页。
     Why: the panel's entire value is that what you see is real; caching would
          turn it into just another mock page.

  4. SSE 而不是 WebSocket
     SSE rather than WebSocket
     理由：事件是单向推送，SSE 更轻；EventSource 浏览器原生支持，无需额外库。
     Why: events are one-way; SSE is lighter and EventSource is native to the
          browser with no extra library.

  5. 队列满时丢弃最旧事件
     Drop the oldest event when the queue is full
     理由：可观测性不能反噬业务；宁可丢日志也不能阻塞入库。
     Why: observability must never throttle the business; dropping a log line
          beats blocking ingestion.

  6. 管理员密码在服务端校验，前端不存明文
     The admin password is verified server-side, never stored in the frontend
     理由：前端硬编码密码等于公开；门控必须在服务端。
     Why: a hard-coded password in the frontend is public; the gate must live
          on the server.

七、遇到的问题与解决 / 7. Issues and Fixes
================================================================================

  问题 1 / Issue 1：抓取全部源耗时过长导致请求超时
  ------------------------------------------------------------------------------
  现象：一键抓取 12 个源时，前端请求等待超过一分钟。
  Symptom: triggering all 12 sources left the request pending for over a minute.
  原因：抓取在请求线程内串行执行，且每个站点都有网络延迟。
  Cause: fetching ran serially inside the request and each site has network
         latency.
  解决：请求内只做「投递」，真正的抓取与入库由消费者异步完成，接口立即返回
        投递条数。
  Fix: the request now only publishes to the broker; the consumer performs the
       actual fetch and persistence asynchronously, and the endpoint returns the
       dispatched count immediately.

  问题 2 / Issue 2：某个模块长期没有新数据
  ------------------------------------------------------------------------------
  现象：只订阅商业统计的账号，抓取后报告仍提示数据来自两周前。
  Symptom: an account subscribed only to Business Stats still got reports built
           on two-week-old rows after fetching.
  原因：演示源内容固定，哈希不变，被去重跳过；真实财经源的数据归到新闻/金融，
        不会进入商业统计。
  Cause: demo content was static so its hash never changed and it was skipped;
         real finance sources route to News/Finance, not Business Stats.
  解决：演示源加当日日期标记，保证每天有新增；同时一键抓取时自动补齐各模块的
        演示源；报告侧在数据过时时显式提示涉及哪些模块、建议订阅哪些模块。
  Fix: demo items carry a daily marker so rows are added each day; one-click
       fetch backfills missing per-module demo sources; reports now name the
       stale modules and suggest modules that have fresh data.

  问题 3 / Issue 3：离开状态页后仍在轮询并报 403
  ------------------------------------------------------------------------------
  现象：锁定管理员后，控制台仍持续出现 403。
  Symptom: after locking admin mode, 403 responses kept appearing.
  原因：状态页的定时轮询在视图切换时没有清理。
  Cause: the polling timer was not cleared on view switch.
  解决：视图销毁时 clearInterval，并在页面不可见时暂停。
  Fix: clear the interval on view teardown and pause while the page is hidden.

  问题 4 / Issue 4：状态页数字与数据库不一致
  ------------------------------------------------------------------------------
  现象：状态页显示的行数与直接查库的结果对不上。
  Symptom: counts on the panel disagreed with direct database queries.
  原因：早期对分区父表做 count 时统计口径与子表不一致，且部分数字被前端缓存。
  Cause: early counts over the partitioned parent differed in scope and some
         values were cached in the frontend.
  解决：统一以父表 count(*) 为准（PostgreSQL 会自动汇总分区），前端每次进入
        页面重新拉取，不做本地缓存。
  Fix: standardised on count(*) over the parent (PostgreSQL aggregates
       partitions automatically) and the frontend refetches on every entry
       without local caching.

  问题 5 / Issue 5：新闻模块混入虚构内容
  ------------------------------------------------------------------------------
  现象：新闻列表里出现域名 demo.domel.local 的条目。
  Symptom: the news list contained items from demo.domel.local.
  原因：早期为了让每个模块都有数据，给新闻也配了演示源。
  Cause: the news module had been given a demo source so every module had data.
  解决：停用该演示源并清除其数据，新闻只保留真实站点；一键抓取不再补回。
  Fix: disabled that demo source and purged its rows; News now uses real sites
       only and the backfill no longer recreates it.
